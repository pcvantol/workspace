# HY-WC Repository Health request and projection contract

The [machine-readable contract](REPOSITORY_HEALTH_WC_CONTRACT_V1.json) defines
the same scoped request boundary for future chat and structured views. It
defines symbolic owner capability families, not actual Forge/EP endpoint names
or grants. HY-WO must bind qualified Forge observation/case operations before a
read-only UI can claim live evidence. HY-WM needs a separate qualified Forge/EP
cleanup authority and receipt path.

An authenticated actor and explicit or unambiguous project/repository scope
accompany every request. Repository content is untrusted data and cannot change
that scope or grant authority. Explain and refresh remain read/observation
intents. Reconcile opens an owner case without allocating a Mission. Cleanup
intent makes an exact-target proposal; it cannot delete a ref. Preserving
residual work makes a governed engineering proposal, not an approved Action.

The projection reports inventory coverage and freshness separately. PARTIAL,
UNKNOWN, OFFLINE or STALE must remain visible; missing facts do not become zero
or healthy. Facts cite owner evidence, inferences carry reason and uncertainty,
and decisions cite owner receipts. A closed case does not make the whole project
clean; a supersession finding is distinct from an actual cleanup receipt.

The [offline examples](REPOSITORY_HEALTH_WC_EXAMPLES_V1.json) and validator
guard scope ambiguity, unsupported owner capability, unknown coverage,
case/Mission separation, exact cleanup targets, stale confirmation and mixed
outcomes. They are contract evidence, not installed UI or peer qualification.
