## User journey and authority

A selected authorized COMPLETE/CONFIRMED validated Business/Architecture turn
opens a new native proposal panel using the real Candidate source route. Source
summary/provenance and explicit user-authored fields are separate. Nothing is
inferred from the model into criteria, confidence, priorities or effect bounds.
The user chooses an actually authorized proposal ID, supplies every required
field, explicitly selects effect mode/delivery/read paths/write paths and saves.
Optional list fields may deliberately be empty; substantive scope/criteria and
existing typed effect policy remain producer requirements.

Save freezes the exact request before forwarding. Forge owns immutable proposal
revision/digest. Amendment is another explicit save at the observed expected
revision; earlier source/proposals/Candidates/receipts remain unchanged. Preview
shows selected versus latest revision. Loading a saved revision into the form
is explicit; reads do not overwrite unsent user input.

Registration previews and freezes the exact revision/digest/context, objective,
scope/exclusions and proposed effect boundary. Cancellation has no downstream
mutation. Confirmation persists one original operation-ID/request, rechecks
current source/preview, then uses the separate registration route. Only a genuine
operation receipt plus matching current canonical Candidate constitutes success.
Original receipt and current Candidate/status/freshness/allocation are distinct.
No Business/Architecture approval buttons or execution grants exist here.
Registration starts no Mission and advice remains applied:false.
